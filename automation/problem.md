# problem — 문제 분석부터 배포까지 (하네스 중립 명세)

운영 중 발생한 문제를 분석해 해결책을 제시하고, 사용자가 선택한 해결책을 구현해 배포까지 완료한다.

> **이 파일은 하네스 중립 「진실의 원천」이다.** 직접 실행 대상이 아니라 진입 어댑터를 통해 실행된다:
> - Claude Code → `.claude/commands/problem.md`
>
> 하위 절차는 다른 중립 명세를 호출한다: 테스트 동결은 `automation/freeze.md`,
> 배포는 `automation/ship.md`(→ `automation/pipeline.md`).

## 이 문서의 위치 — 운영 변경의 단일 진입점

**운영 중 변경은 무조건 여기서 시작한다.** `/implement`는 스펙이 이미 존재하는 계획된 스텝의
진입점이지, 사람이 고르는 갈림길이 아니다.

그 이유는 **버그 리포트 시점에는 원인을 모르기 때문**이다. "영문 화면인데 근거가 한국어로 나온다"가
요청 헤더 누락인지 응답 소비측 분기 결함인지는 진단해봐야 안다. 그런데 하네스 선택은 그 답에
의존한다 — 따라서 **라우팅은 진단 뒤(Phase 1.5)에 기계적으로 판정**하며, 사람이 사전에 고르지 않는다.

> **이 레포의 승격은 BE 레포를 거친다.** 스펙은 여기 없다(`/implement` Phase 0) — `docs/specs/`는
> BE 레포에 있다. 따라서 게이트가 승격을 판정해도 **이 세션이 스펙을 쓸 수 없다.** 승격은 「진단
> 결과를 BE 세션의 `/spec`에 넘기는 것」이며 그 형식은 「승격 핸드오프」가 정한다. 넘긴 뒤 이 절차는
> 끝나고, 스펙이 착지하면 `/implement <번호>`가 **새로 시작**한다 — 이어받지 않는다.
> BE판보다 승격 비용이 비싸므로 게이트는 그만큼 좁게 잡혀 있다 — Phase 1.5의 표가 전부다.

## Preflight

1. `gh auth status` — 인증 실패 시 **중단**.
2. `git fetch origin main` — 이후 모든 비교는 **`origin/main` 기준**이다. 로컬 `main`은 뒤처져 있을 수 있다.
3. `git status --porcelain` — 비어 있지 않으면 **이월 변경을 stash로 분리**한다:
   - `git stash push -u -m "problem-preflight-stash"` (untracked 포함), `HAS_STASH=true`
   - **이 변경이 이번 문제와 관련 있는지 사용자에게 확인한다.** BE판은 무조건 워킹 트리로 복원하지만
     이 레포는 `main` = 프로덕션이라 **무관한 변경이 프로덕션에 실리는 비용이 다르다.**
     `automation/pipeline.md` Step 1이 `git add -A`로 워킹 트리를 통째로 쓸어담으므로, 분리하지
     않으면 이번 배포에 그대로 따라 나간다.
     - **관련 있음** → Phase 3에서 브랜치 생성 직후 `git stash pop`으로 복원해 WIP 커밋으로 승격한다.
     - **무관함** → stash에 **둔 채로** 전 Phase를 진행하고, Phase 6의 배포 성공 후 복원한다.
       stash 상태가 워킹 트리를 clean하게 유지하므로 병렬 워크트리 통합(cherry-pick)에도 유리하다.
4. `git checkout main && git pull origin main` — 항상 최신 `main`에서 시작한다.

## Phase 1: 문제 분석 & 해결책 제시

> **단순 변경 스킵**: 사용자가 구체적인 변경 내용을 직접 명시한 경우(예: "토글 아이콘 회색을
> 메뉴 아이콘과 맞춰줘") Phase 1을 스킵하고 단일 작업으로 구성해 Phase 1.5로 직행한다.

1. 제시된 증상·에러·스크린샷을 분석한다. 프로덕션 화면 문구는 대개 원인을 뭉뚱그리므로,
   **화면만 보고 원인을 단정하지 않는다** — 필요하면 BE 로그 확보를 사용자에게 요청한다.
2. 관련 코드를 탐색해 원인을 파악한다. 계약의 형태는 문서가 아니라
   `src/shared/api/generated/schema.ts`에서, 화면 구조는 해당 `features/*`에서 확인한다.
3. 해결책을 번호와 함께 제시한다. 하나의 해결책 안에 동작 변경과 표층 변경이 섞일 수 있으므로
   **해결책 내부를 작업(task) 단위로 분리**한다.

   ```
   해결책 N: [한 줄 요약]
   ├─ 작업 N-a [동작]    변경 내용    | 영향 파일: src/features/ask-guideline/model/stream-state.model.ts
   ├─ 작업 N-b [비동작]  변경 내용    | 영향 파일: src/app/(protected)/assistant/_components/…
   └─ 작업 N-c [동작]    변경 내용    | 영향 파일: ...
   위험도: 낮음 / 중간 / 높음
   ```

   작업 분류 기준 — **"이 변경이 옳게 됐는지를 테스트가 단언할 수 있는가"** 하나로 가른다:
   - `[동작]`: 화면 동작·데이터 흐름·상태 전이가 관측 가능하게 바뀐다. `features/**`·`widgets/**`·
     `app/**`의 로직, `shared/api/`의 소비 계층, `shared/lib/**`, `shared/i18n/**`의 키·해석 로직
     → Test-First 절차 (`automation/freeze.md`)
   - `[비동작]`: 단언해봐야 값을 복붙하는 토톨로지가 되는 것. 시각 표현(Tailwind 클래스·CSS),
     키 구조가 그대로인 문구 교체, 설정·문서·`scripts/**`·`.github/**`·`automation/**`
     → 일반 코드 변경 절차

   이 레포의 `[BUG]` 표본이 그대로 실증이다 — #90(화면 복귀 시 답변 진행 상태를 알 수 없음)은
   스트리밍 복구 흐름(`docs/architecture.md` §4)이라 `[동작]`, #87(영문 화면에 한국어 근거)은
   언어 전달 경로라 `[동작]`, #93(온보딩이 짚는 카드 테두리가 세 변에서 잘림)은 clip 경계라
   DOM 단언이 닿지 않아 `[비동작]`이다.

   **영향 파일 목록은 Phase 1.5의 입력이므로 빠짐없이 적는다.**

4. **사용자 확인 대기** — 적용할 해결책 번호 선택 요청 (예: "1, 3번 적용")

## Phase 1.5: 라우팅 판정 (기계 검사)

선택된 해결책의 **영향 파일 전체**를 아래 게이트에 대조한다. 사람의 해석이 아니라 경로 매칭이다.

| 게이트 | 경로 패턴 | 걸리면 |
|---|---|---|
| **계약** | `openapi/**`, `src/shared/api/generated/**` | **BE 레포 이관** |
| **전송·인증** | `src/shared/api/http.ts`, `src/shared/api/api-client.ts`, `src/shared/api/stream-client.ts`, `src/features/auth/**` | **스펙 승격** |
| **새 feature** | `src/features/<기존에 없던 디렉토리>/`, `src/widgets/<기존에 없던 디렉토리>/` | **스펙 승격** |

**하나라도 걸리면 이 절차를 중단**하고 아래 「승격 핸드오프」를 산출한다. 중단 시점에는 아직 브랜치를
만들지 않았으므로(Phase 3 이전) 정리할 잔재가 없다. 걸리지 않으면 Phase 2로 진행한다.

**계약 게이트는 BE판과 성격이 다르다.** BE에서 이 게이트는 "계약을 바꾸려 하니 스펙으로 합의하라"는
뜻이지만, 여기서는 그 파일들이 **codegen 산출물이라 수동 편집 자체가 금지**다(`docs/architecture.md` §3,
CI `codegen-check`의 재생성 diff = 0 검사가 강제). 즉 이 게이트에 걸린 문제는 **FE에서 고칠 수 있는
문제가 아니다** — 계약이 부족한 것이므로 BE 레포로 넘긴다. 여기서 스펙을 쓰는 것은 순서가 틀렸다.

**전송·인증 게이트의 근거는 이 레포에서 유독 무겁다.** http.ts의 401 → refresh single-flight는 앱
전체가 공유 promise 하나로 돌고(§2), stream-client는 그 `ensureRefreshed()`를 그대로 쓴다 — 한 줄이
전 화면의 인증 흐름을 바꾼다. 게다가 **로컬 dev 서버는 세션을 만들지 못해 인증 경로를 실제로 밟아볼
수 없다.** 진단 루프 자체가 돌지 않는 영역이라, 임기응변의 위험이 다른 곳보다 크다.

- **오탐은 안전한 방향이다**: 전송 계층 파일을 건드렸지만 주석 수정이라 동작이 그대로인 경우, 스펙을
  한 번 더 쓰는 비용이 발생할 뿐이다. 진짜 계약 파괴 여부는 `pnpm api:generate` + CI의 `codegen-check`가
  최종 판정한다 — 이 게이트는 그 앞단의 값싼 필터다.
- **통과**했으면 판정 결과를 사용자에게 **한 줄로 보고**한 뒤 Phase 2로 진행한다. **걸렸으면** 한 줄
  보고로 끝내지 않고 「승격 핸드오프」 블록까지 내놓는다 — 진단을 여기까지 한 세션이 그 내용을 넘기지
  않으면, 받는 쪽이 처음부터 다시 조사한다.

### 산출 뒤

1. 블록을 사용자에게 전달하고 **BE 세션에서 `/spec`으로 이어가야 함을 명시**한다. `/spec`은

## Phase 2: 의존성 분석 & 실행 계획

1. 선택된 해결책의 모든 작업을 평탄화해 목록을 만든다.
2. 작업 간 의존성을 분석한다:
   - **같은 파일 수정** → 순차
   - **같은 feature의 연관 로직 변경** → 순차
   - **서로 다른 feature·파일을 독립 변경** → 병렬 가능
3. 실행 계획을 보고한다 (병렬 그룹 A/B, 순차 그룹 C 형태로 그룹핑, 각 작업의 타입과 절차 명시).
4. 보고 후 **사용자 확인 없이** 즉시 Phase 3으로 진행한다.

## Phase 3: 브랜치 (이슈 생성 없음)

코드 변경 **전에** 브랜치를 만든다 — 병렬 워크트리의 base가 필요하기 때문이다.

1. 변경 성격에 맞는 타입을 고른다 (`automation/ship.md` Phase 1의 타입 테이블이 원천).
   **이 하네스의 기본값은 `[BUG]`(`bug/`)다** — 운영에서 관측된 문제로 진입하는 경로이기 때문이다.
   배포 전에 자체 발견한 것을 여기로 가져왔다면 `[FIX]`(`fix/`)로 고른다. 이 구분은 표본을 세기
   위한 것이므로 편의로 뭉개지 않는다.
2. 브랜치 `<prefix>/<슬러그>` 생성 → checkout. 슬러그는 짧은 **영문 kebab-case**.
3. **이슈를 만들지 않는다** (`automation/ship.md` 「워크플로우 전제」 — 이 레포는 PR-퍼스트다).
   BE판과 달리 브랜치명에 `#`이 없으므로 git/gh 명령의 따옴표 방어도 필요 없다.

   > **커밋 제목에 `#`를 쓰지 않는다.** 이슈가 없어 `#N`에 넣을 번호가 없고, 임의의 번호를 `#`와 함께
   > 쓰면 **GitHub이 같은 번호의 PR로 자동 링크한다** — `[TEST/#09]`·`[TEST/#10]`·`[TEST/#11]`이
   > 각각 PR #9·#10·#11에 잘못 걸린 전례가 이 레포에 있다. squash 머지가 붙이는 `(#PR번호)`가
   > 추적 식별자다.

4. **Preflight 이월 변경 처리**: Preflight 3에서 **관련 있음**으로 확인된 stash만 여기서 복원한다:
   `git stash pop` → `git add -A && (git diff --cached --quiet || git commit -m "wip: preflight carry-over")`
   - 이는 병렬 통합(cherry-pick)의 전제조건이다. 더티 워킹 트리 위에서 cherry-pick하면
     `error: your local changes would be overwritten`으로 실패하고, 병렬 워크트리에는 이 변경이 없어
     의미적 충돌이 통합 시점까지 감지되지 않는다.
   - 충돌 시 자체 해결한 뒤 진행하고, 해결 내역을 사용자에게 보고한다.
   - **무관함**으로 분류된 stash는 손대지 않는다 — Phase 6까지 stash에 남는다.
   - 이 WIP 커밋을 따로 정리할 필요는 없다. `automation/pipeline.md`가 **squash 머지**를 쓰므로
     브랜치의 커밋들은 머지 시점에 하나로 합쳐진다 (BE판의 명시적 squash 지시가 여기선 불필요하다).

> **중단 시 정리**: Phase 3부터는 브랜치가 존재하므로, 이후 단계가 실패하거나 사용자가 중단하면
> 브랜치 삭제 여부를 확인한다. 이슈가 없으므로 닫을 것은 없다.

## Phase 4: 코드 변경

### 사전 단계: 테스트 동결 (`[동작]` 작업 대상)

`automation/freeze.md`를 읽고 아래 파라미터로 실행한다. **`[동작]` 작업이 없으면 이 단계 전체를 스킵**한다.

| 파라미터 | 값 |
|---|---|
| 명세 | Phase 1에서 확정된 해당 작업의 변경 내용 + `docs/architecture.md`의 관련 § |
| 작업 ID | **브랜치 슬러그** (이슈 번호가 없다) |
| 동결 단위 | `[동작]` 작업 1개 = 1 단위 (전 단위 완료 후 커밋·목록 기록 1회) |
| 참조 패턴 파일 | `src/shared/api/http.test.ts` + 대상 화면의 기존 `*.test.tsx` 1~2개 전문 |

`automation/freeze.md`의 커밋 제목은 `[TEST] spec <번호> …` 형식이지만 **이 경로에는 스펙 번호가
없다.** 대신 **`[TEST] <슬러그> <요약> 수용 기준 테스트 동결 (작성: Codex)`**를 쓴다. `#` 금지 규칙은
그대로 승계한다.

동결은 **구현(병렬/순차) 시작 전에 완료**한다.

### 실행 모드

- **그룹 2개 이상** → 각 그룹을 에이전트로 병렬 실행. 통합 완료 전까지 메인 세션은 코드를 직접
  수정하지 않고 **cherry-pick 통합만** 담당한다.
- **그룹 1개** → 워크트리 없이 메인 세션에서 순차 실행.

### 병렬 실행

- **base**: 각 워크트리는 반드시 **현재 브랜치의 HEAD**에서 생성한다. 동결 커밋·WIP 커밋이 HEAD에
  포함돼야 재현·컴파일이 가능하다.
- **네이밍**: 워크트리 내 임시 브랜치 `wt/<슬러그>-<그룹>`(예: `wt/answer-progress-A`).
- **에이전트 프롬프트에 포함할 것**: 그룹의 작업 상세, 타입별 절차 전문, 그룹 내부 순서,
  **커밋 소유권**(작업마다 워크트리 내 로컬 커밋 + 완료 보고에 **커밋 SHA 목록 순서대로 필수** —
  메인 세션이 cherry-pick 대상을 수집하는 유일한 경로), push·PR 금지.
- **e2e 경합 방지 — 이 레포에서는 단순 포트 충돌보다 나쁘다.** `playwright.config.ts`는 포트를
  **3101로 고정**하고 로컬에서 `reuseExistingServer: true`다. N개 워크트리가 동시에 `pnpm test:e2e`를
  돌리면 뒤에 온 워크트리는 **자기 빌드가 아니라 먼저 뜬 워크트리의 서버에 대고 테스트를 통과시킨다** —
  실패하며 시끄럽게 죽는 게 아니라 **조용히 잘못된 대상을 검증한다.** 따라서 병렬 에이전트는
  **e2e를 실행하지 않고** 구현 + `pnpm typecheck && pnpm test && pnpm build`까지만 수행한다.
  e2e 실제 실행은 통합 후 메인 세션이 일괄 수행한다(Phase 5).
- **동결 목록**: 워크트리는 동결 커밋을 포함한 HEAD에서 생성되므로 상태 파일이 자동 포함된다.
  상대 경로로 기록돼 있어 워크트리 루트 기준으로 훅이 정상 매칭한다.
- **통합**: 모든 에이전트 완료 후 보고된 SHA를 **그룹 알파벳 순(A→B→C)**, 그룹 내부는 보고 순서로
  cherry-pick한다 (독립 그룹이라 이론상 순서 무관하지만 충돌 해결의 재현성을 위해 고정).
  통합 직후 `pnpm typecheck && pnpm build`로 통합 검증하고, 각 워크트리를 `git worktree remove` +
  임시 브랜치 삭제한다.

### `[동작]` Test-First 구현 절차

1. 동결된 테스트·fixture를 읽고 기대하는 인터페이스와 동작을 파악한다
2. 명세 + 동결 테스트를 참조해 스텁 본문을 구현한다. 구현 중 새 시그니처가 필요해지면 테스트에
   맞춰 임의 생성하지 않는다 — 작업 명세와 스텁을 먼저 갱신하고 재파생·재동결한 뒤 재개한다
3. 테스트 실행 → 실패 시 **구현을 수정**해 재실행 (테스트는 동결 상태라 수정 불가)
4. 이의 제기는 `automation/freeze.md`의 「이의 제기(TEST-DISPUTE)」를 따른다
5. `pnpm typecheck && pnpm test`

### `[비동작]` 일반 절차

1. 변경 적용 → `pnpm typecheck && pnpm build`
2. **기존 테스트 영향 검증**: 변경 대상을 의존하는 기존 테스트를 실행한다(공용 UI·`app-shell`·
   providers 변경 시 특히 주의). 실패하면 테스트를 수정하되, **동결된 테스트에 영향이 가면 수정하지
   말고** TEST-DISPUTE에 준해 보고한다 (훅이 Edit/Write를 차단하므로 어차피 직접 수정 불가).
   영향받는 테스트가 없으면 스킵.
3. 변경 파일 재검토: 타입 오류, import 누락, 의존 방향(`app → widgets → features → shared`) 준수

### 계약 이탈 감지 (모든 작업 공통)

구현 중 **Phase 1.5의 게이트에 해당하는 변경이 필요해지면 그 자리에서 중단**하고 사용자에게 보고한다.
임의로 진행하지 않는다 — 진단 단계에서 보이지 않던 계약·전송 계층 변경이 구현 중 드러난 것이므로,
이관·승격 여부를 사람이 결정해야 한다.

> 이는 동결 테스트를 고치고 싶어질 때 TEST-DISPUTE로 멈추는 것과 같은 원리다 — **하네스는 스스로
> 경계를 넘지 않는다.**

**승격을 택하면 브랜치를 버린다.** Phase 1.5와 달리 여기서는 브랜치·동결 커밋·부분 구현이 이미
존재하는데, 그것을 들고 갈 곳이 없다:

- `/implement` Phase 0은 `git status` clean 확인 → `main` checkout → **새 브랜치 생성**이다.
  남겨 둔 브랜치를 이어받는 경로가 애초에 없다.
- 부분 구현이 남아 있으면 `/implement` Phase 2의 「구현이 이미 존재하면 중단하고 보고한다」 가드에
  **하네스 우회 신호로 오탐**된다. 그 가드는 되돌리는 절차를 일부러 두지 않는다.
- 동결 테스트는 **미확정 명세에서 파생된 심판**이다. 스펙이 확정되면 `/implement` Phase 2가 그
  스펙으로 다시 파생한다 — 여기서 만든 것을 물려주면 잘못된 기준을 확정된 것처럼 넘기는 셈이다.

**버리는 것은 브랜치이지 알아낸 것이 아니다.** 순서를 지킨다:

1. 「승격 핸드오프」 블록을 먼저 산출한다 — 브랜치를 지우기 전에 진단 결과를 건져낸다.
2. `automation/freeze.md`의 「동결 해제」를 수행한다. 그 규칙은 「머지(또는 배포) 성공 후에만」이지만
   **폐기에 의한 해제가 그 유일한 예외**다 — 해제하지 않으면 훅이 남은 목록으로 이후 세션의 Edit까지
   계속 막는다.
3. `git checkout main` → `git branch -D "<브랜치명>"`. push한 적이 있으면 원격 브랜치도 지운다.
4. 사용자에게 블록과 함께 **브랜치를 버렸다는 사실**을 보고한다.

## Phase 5: 통합 & 검토

1. 전체 변경사항 보고: 작업별 변경 파일, 테스트 결과 요약
2. **최종 검증** — `automation/ship.md` Phase 2의 게이트와 **같은 순서**로 돌고, 거기에 e2e를 더한다:

   ```
   pnpm api:generate
   git diff --exit-code openapi src/shared/api/generated   # 드리프트 0
   pnpm typecheck
   pnpm typecheck:design-sync
   pnpm test
   pnpm test:e2e
   pnpm build
   ```

   - **e2e를 여기서 도는 이유는 병렬 실행이 그것을 미루도록 설계돼 있기 때문이다.** Phase 4는 병렬
     에이전트에게 e2e를 **금지**한다(포트 3101 고정 + `reuseExistingServer`가 남의 서버를 검증하게
     만들므로). 구조적으로 미룬 대가를 갚는 자리가 여기이고, **통합된 트리에서 e2e를 처음 밟는
     지점**이 이 단계다.
   - **로컬이 CI보다 엄격하다.** `playwright.config.ts`가 `retries: CI ? 1 : 0`,
     `workers: CI ? 2 : undefined`라 로컬 실행은 재시도 없이 더 많은 워커로 돈다 — flaky와 경합을
     CI보다 잘 드러낸다. 여기서만 보이는 실패가 실재한다.
   - **다만 마지막 방어선은 아니다.** e2e는 `.github/workflows/ci.yml`의 잡이자 `main` 브랜치 보호의
     required check다 (실측 5개: `codegen-check`·`gitleaks`·`Vercel`·`e2e`·`scripts`). 여기서
     빠뜨려도 프로덕션에 새지 않고 **PR 왕복이 한 번 더 늘 뿐**이다. 그래도 그 왕복은 수 분이고,
     아래 수정 루프가 CI 안에서 돌면 매 회차가 그만큼 비싸진다.

     > 2026-09-03 정정. `#96`이 이 하네스를 들이면서 「e2e는 CI에 없다 … 유일한 방어선」이라고
     > 적었는데, e2e 잡은 그보다 74개 PR 앞선 `#22`에 이미 있었다. 낡은 게 아니라 **`ci.yml`을
     > 확인하지 않고 쓴 문장**이다. 정작 맞는 근거(병렬 실행이 미룬 대가)는 같은 줄 뒤편에 이미
     > 적혀 있었다 — 근거를 지어내지 말고 옆에 있는 것을 쓸 것.
   - **테스트 실패는 이 시점의 정상 경로다**: 병렬 에이전트는 자기 구현의 e2e GREEN을 확인한 적이
     없다. 실패 시 사용자에게 떠넘기고 멈추지 않는다 — **동결을 유지한 채 구현만 수정**하고 재실행하는
     루프를 GREEN까지 반복한다.
   - **루프 내 재실행은 실패분만 대상**으로 한다. 전부 GREEN이 된 뒤 최종 확인으로 전 구간 1회 재실행.
   - **서킷 브레이커**: 동일 테스트가 **3회 연속** 실패하면 루프를 멈추고 현황(실패 테스트, 시도한
     수정, 원인 분석)을 보고한 뒤 지시를 대기한다.
   - 라우트가 바뀐 변경이면 `pnpm typecheck` 전에 `rm -rf .next` — stale `.next/types`가 옛 라우트를
     참조해 헛실패한다.
3. **동결 무결성 사후 감사**: 동결이 있었으면 `automation/freeze.md`의 「사후 감사」를 실행한다.
   감사는 항상 마지막 코드 변경 뒤에 오며, 이후 코드가 다시 바뀌면 재실행한다.
4. **디자인 드리프트 선판정**: `automation/bin/design-drift.sh` 실행 (아래 「디자인 시스템 재동기화」).
5. **사용자 확인 대기** — 추가 수정 요청 시 반복. OK 시에도 **동결은 아직 해제하지 않는다**
   (배포 실패로 재수정하는 시나리오에서 테스트가 무방비가 되지 않도록).

   > **이 확인을 생략하지 않는다.** Phase 6이 `automation/ship.md`에 위임하면 ship Preflight가 feature
   > 브랜치를 감지해 **Phase 1·3을 스킵**하므로 ship이 가진 사용자 확인이 건너뛰어지고, 이후
   > `automation/pipeline.md`가 PR → 머지 → **Vercel 프로덕션 배포**까지 멈추지 않는다. 이 레포는
   > `main` = 프로덕션이라 되돌릴 창이 BE보다 좁다.

## Phase 6: 배포

`automation/ship.md`를 읽고 실행한다. 현재 feature 브랜치에 있으므로 ship의 Preflight가 이를 감지해
**Phase 1·3을 스킵하고 Phase 2(검증)로 직행**한다.

전달할 컨텍스트: 브랜치명, 타입, Phase 5의 변경사항 요약, 그리고 **Phase 5-2 검증 완료 사실**
(전 구간 green 여부) — ship Preflight의 검증 스킵 판정 입력이다.

**배포 성공 후**:
1. `automation/freeze.md`의 「동결 해제」를 수행한다.
2. Preflight에서 **무관함**으로 분류해 stash에 남겨둔 이월 변경이 있으면 `git stash pop`으로 복원하고,
   복원 사실을 보고한다. 배포가 실패해 재수정하는 동안은 stash를 그대로 둔다.

## 디자인 시스템 재동기화

BE판의 「파괴적 DB 마이그레이션 2단계 배포」가 차지하던 자리를 이 레포에서는 이 게이트가 차지한다 —
**배포보다 먼저 와야 하는 외부 절차**라는 점에서 성격이 같다.

`.design-sync/config.json`의 `componentSrcMap`(및 `.design-sync/drift-watch.json`)에 등록된 컴포넌트를 고치면
claude.ai/design 재동기화를 마쳐야 배포할 수 있다. 재동기화가 고치는 `config.json`·`previews/`가
커밋 대상이라 같은 배포 커밋에 실려야 한다 (`automation/ship.md` 「워크플로우 전제」).

- Phase 1에서 해결책이 등록된 컴포넌트를 건드리면 **그 사실을 해결책에 명시**한다.
- Phase 5-4에서 `automation/bin/design-drift.sh`를 **미리** 돌린다. ship Preflight가 어차피 판정하지만,
  거기서 걸리면 Phase 5의 전 구간 검증(e2e 포함, 수 분)을 다 돌린 뒤 중단이다. 앞당겨 판정하면
  그 비용을 버리지 않는다.
- `result=DRIFT` → 재동기화가 필요하다고 보고하고 대기한다. **재동기화 자체는 이 절차가 수행하지
  않는다** — Claude Code 전용 도구와 사람이 승인하는 업로드가 필요해 하네스 중립이 아니다.
  절차는 `.design-sync/NOTES.md`의 「재동기화 한 줄 요약」이 원천이다.

## 규칙

- 해결책 제시 시 코드 변경 없이 분석만 수행한다
- 사용자가 선택하지 않은 해결책은 절대 적용하지 않는다
- **승격 판정 시 브랜치를 남기지 않는다** — 「승격 핸드오프」로 진단 결과만 넘기고, 브랜치·동결·
  부분 구현은 폐기한다. BE 레포에는 이 하네스가 직접 쓰지 않는다
- 하나의 해결책 안에서도 `[동작]`/`[비동작]` 작업을 반드시 분리해 제시한다
- `[동작]` 테스트 실패 시 구현을 수정한다 — **기본 추정은 구현 결함, 입증 책임은 구현 쪽**
- **API 3계층을 넘나들지 않는다** (§2): 전송(`http.ts`) → 봉투 해석(`api-client.ts`) →
  소비(`features/*/api/`). feature는 fetch를 직접 부르지 않는다
- `shared/api/generated/`·`openapi/`는 codegen 산출물이다 — **수동 편집 금지** (§3).
  수동 DTO를 만들지 않는다 — 타입은 전부 `generated/schema.ts`에서 가져온다
- enum에 exhaustive switch를 쓸 때 `default`를 반드시 둔다 (§3 전방 호환)
- **토큰이 FE 코드·스토리지에 등장하면 안 된다** (§2) — HttpOnly 쿠키로만 존재한다
- 테스트는 MSW로 모킹한다 — 수동 mock 금지 (§5). e2e 하네스는 **미스텁 요청을 실패로 잡으므로**
  새로 부르는 엔드포인트가 생기면 해당 spec의 스텁도 함께 추가한다
- 새 사용자 문구는 i18n 사전을 거친다 — 화면에 하드코딩된 한국어를 남기지 않는다
- **커밋 제목에 `#`를 쓰지 않는다** (Phase 3의 자동 링크 오작동)
- 상태 파일은 `.cure-implement/`(git-ignored)를 `/implement`와 공유한다
- 모든 `gh`/`git` 명령 실패 시 에러 내용을 사용자에게 보고한다
